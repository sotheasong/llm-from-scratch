## Chapter 1 — Understanding Large Language Models

### 1.1 What is an LLM?
A deep neural network trained on massive text to understand/generate human-like text.
- **"Large"** = both parameter count (10s–100s of billions) *and* dataset size.
- Training objective is deceptively simple: **next-word prediction**. It works because language is inherently sequential, so predicting the next token forces the model to learn context, structure, and relationships.
- Hierarchy: `AI ⊃ Machine Learning ⊃ Deep Learning ⊃ LLMs`.
- Key difference vs. classical ML: **no manual feature extraction**. Old spam filters needed hand-crafted features ("count of the word *free*", "number of `!`"); deep nets learn features themselves.
- Older NLP models were narrow (one model per task). LLMs are broadly capable across tasks.

### 1.2 Applications
Translation, text generation, sentiment analysis, summarization, code generation, chatbots, knowledge retrieval over specialized corpora (medicine, law).

### 1.3 The two training stages

```
Raw unlabeled text ──[pretraining]──> Base / Foundation model ──[fine-tuning]──> Task model
```

**1. Pretraining** — on a huge corpus of *raw* (unlabeled) text.
- Uses **self-supervised learning**: the model generates its own labels from the data. The label for a sequence is just the next word in it. This is why unlabeled internet text is usable at all.
- Output = a **base / foundation model** (e.g. GPT-3). Capable of text completion and limited few-shot learning.

**2. Fine-tuning** — on a smaller *labeled* dataset. Two main flavors:
- **Instruction fine-tuning** — dataset of (instruction, answer) pairs. E.g. `("translate this to German: ...", "...")`.
- **Classification fine-tuning** — dataset of (text, class label) pairs. E.g. `(email, "spam")`.

**Why build a custom LLM?** Domain-specific models can beat general ones (BloombergGPT for finance); data privacy; on-device deployment (lower latency/cost); full control over updates.

### 1.4 The transformer architecture
From *"Attention Is All You Need"* (2017), originally built for **machine translation**.

Two submodules:
- **Encoder** — processes input text → vectors capturing contextual info.
- **Decoder** — takes those vectors → generates output text.

Both are stacks of layers connected by **self-attention**: the mechanism that lets the model weigh the importance of every token relative to every other token. This is what captures long-range dependencies. (Implemented in Ch. 3.)

**Two lineages:**

| | BERT | GPT |
|---|---|---|
| Built from | Encoder | Decoder |
| Trained on | **Masked** word prediction (fill in hidden words) | **Next**-word prediction |
| Direction | Bidirectional | Unidirectional, left→right |
| Good at | Classification, sentiment, toxicity detection | Text generation |

> **Transformers ≠ LLMs.** Not all transformers are LLMs (they're also used in vision), and not all LLMs are transformers (there are recurrent/convolutional variants aimed at efficiency). In this book "LLM" means a GPT-like transformer.

### 1.5 Training data scale
GPT-3's pretraining mix (~499B tokens available, but only **300B** actually used — the paper never says why):

| Dataset | Tokens | Share |
|---|---|---|
| CommonCrawl (filtered) | 410B | 60% |
| WebText2 | 19B | 22% |
| Books1 | 12B | 8% |
| Books2 | 55B | 8% |
| Wikipedia | 3B | 3% |

A **token** ≈ a word or punctuation character. CommonCrawl alone is ~570 GB. Estimated GPT-3 pretraining cost: **~$4.6M** in cloud credits — hence the value of open weights + cheap fine-tuning.

### 1.6 The GPT architecture
- **Decoder only** — the encoder is dropped entirely. Simpler than the original transformer, just much bigger (GPT-3: 96 layers, 175B params, vs. the original transformer's 6 encoder + 6 decoder blocks).
- **Autoregressive**: each generated word is fed back in as input for the next prediction. This is why output stays coherent.
- **Emergent behavior**: GPT can translate, classify, and summarize despite never being explicitly trained to. These abilities emerge from scale + data diversity.
- **Zero-shot** = performs an unseen task with no examples. **Few-shot** = learns from a handful of examples supplied in the prompt.

### 1.7 The plan (3 stages)
1. Data preprocessing + attention mechanism + architecture (Ch. 2–4)
2. Pretraining loop → foundation model + evaluation; also loading open weights (Ch. 5)
3. Fine-tuning → classifier or instruction-following assistant (Ch. 6–7)

## Chapter 2 — Working with Text Data

The full input pipeline this chapter builds:

```
raw text → tokens → token IDs → token embeddings → + positional embeddings → input embeddings
```

### 2.1 Word embeddings
Neural nets can't consume text — it's categorical, not numeric. **Embedding** = mapping discrete objects (words) to points in a continuous vector space.

- **Word2Vec** was the classic approach: train a net to predict a word's context (or vice versa). Core intuition — *words appearing in similar contexts have similar meanings* — so related words cluster in the vector space.
- **But LLMs don't use Word2Vec.** They learn their *own* embedding layer as part of the input layer, updated during training, so embeddings are optimized for the specific task and data.
- Dimensionality is a performance/efficiency tradeoff: GPT-2 small = **768** dims; GPT-3 = **12,288** dims.

### 2.2 Tokenizing text
Sample corpus: *"The Verdict"* by Edith Wharton (public domain, ~20,479 chars).

```python
import re

# Split on whitespace only — punctuation stays glued to words. Not good enough.
re.split(r'(\s)', "Hello, world. This, is a test.")
# ['Hello,', ' ', 'world.', ' ', 'This,', ...]

# Split on whitespace AND punctuation:
re.split(r'([,.]|\s)', text)
# ['Hello', ',', '', ' ', 'world', '.', ...]  <- empty strings + whitespace left over
```

Final scheme — handles the full punctuation set plus em-dashes, and strips whitespace:

```python
preprocessed = re.split(r'([,.:;?_!"()\']|--|\s)', raw_text)
preprocessed = [item.strip() for item in preprocessed if item.strip()]
# len(preprocessed) == 4690 tokens
# ['I', 'HAD', 'always', 'thought', 'Jack', 'Gisburn', 'rather', 'a',
#  'cheap', 'genius', '--', 'though', ...]
```

Two design notes:
- **Don't lowercase.** Capitalization helps the model distinguish proper nouns and learn sentence structure.
- **Dropping whitespace** saves memory/compute, but keep it if the exact structure matters (e.g. Python source code, where indentation is semantic).

### 2.3 Tokens → token IDs
Build a **vocabulary**: sort the unique tokens, map each to an integer.

```python
all_words = sorted(set(preprocessed))
vocab = {token: integer for integer, token in enumerate(all_words)}
len(vocab)  # 1130
```

```python
class SimpleTokenizerV1:
    def __init__(self, vocab):
        self.str_to_int = vocab
        self.int_to_str = {i: s for s, i in vocab.items()}   # inverse map, for decode

    def encode(self, text):
        preprocessed = re.split(r'([,.:;?_!"()\']|--|\s)', text)
        preprocessed = [item.strip() for item in preprocessed if item.strip()]
        return [self.str_to_int[s] for s in preprocessed]

    def decode(self, ids):
        text = " ".join([self.int_to_str[i] for i in ids])
        return re.sub(r'\s+([,.?!"()\'])', r'\1', text)      # kill space before punctuation
```

Every tokenizer has this same `encode` / `decode` pair. Round-tripping works — **until an unseen word appears**:

```python
tokenizer.encode("Hello, do you like tea?")   # KeyError: 'Hello'
```

"Hello" isn't in *The Verdict*, so it isn't in the vocab. This motivates special tokens.

### 2.4 Special context tokens
Add two entries to the vocabulary (size 1130 → **1132**):

- `<|unk|>` — stands in for any out-of-vocabulary word.
- `<|endoftext|>` — separates unrelated documents. When training on many books concatenated together, this marker tells the model the sources aren't continuous.

```python
all_tokens = sorted(set(preprocessed))
all_tokens.extend(["<|endoftext|>", "<|unk|>"])
vocab = {token: integer for integer, token in enumerate(all_tokens)}
```

`SimpleTokenizerV2` differs only in `encode`, adding one line:

```python
preprocessed = [item if item in self.str_to_int else "<|unk|>"
                for item in preprocessed]
```

```python
text = " <|endoftext|> ".join(("Hello, do you like tea?",
                              "In the sunlit terraces of the palace."))
tokenizer.decode(tokenizer.encode(text))
# '<|unk|>, do you like tea? <|endoftext|> In the sunlit terraces of the <|unk|>.'
```

Other special tokens seen in the wild: `[BOS]` (beginning of sequence), `[EOS]` (end of sequence), `[PAD]` (pad short sequences up to batch length).

**GPT uses none of these.** It only has `<|endoftext|>`, which doubles as `[EOS]` *and* as padding — the padding choice is irrelevant because padded positions are masked out during attention. GPT also has no `<|unk|>`, because BPE makes it unnecessary.

### 2.5 Byte pair encoding (BPE)
The tokenizer actually used by GPT-2, GPT-3, and the original ChatGPT.

**How it works:** start with all individual characters in the vocabulary, then iteratively merge frequently co-occurring pairs into subwords, and frequent subwords into words (e.g. `d` + `e` → `de`, common in *define*, *depend*, *made*). Merges are chosen by a frequency cutoff.

**Why it matters:** an unknown word is decomposed into known subwords or individual characters. So BPE can encode *any* string — no `<|unk|>` needed, and the model can process text containing words it never saw in training.

```python
# pip install tiktoken
import tiktoken
tokenizer = tiktoken.get_encoding("gpt2")

text = "Hello, do you like tea? <|endoftext|> In the sunlit terraces of someunknownPlace."
ids = tokenizer.encode(text, allowed_special={"<|endoftext|>"})
# [15496, 11, 466, 345, 588, 8887, 30, 220, 50256, 554, 262, 4252, 18250,
#  8812, 2114, 286, 617, 34680, 27271, 13]
tokenizer.decode(ids)   # round-trips perfectly, including "someunknownPlace"
```

GPT-2's BPE vocabulary is **50,257** tokens; `<|endoftext|>` gets the highest ID, **50256**.

### 2.6 Data sampling with a sliding window
Training pairs are trivially constructed: **the target is the input shifted right by one position.**

```python
enc_text = tokenizer.encode(raw_text)   # 5145 tokens for the whole story
enc_sample = enc_text[50:]

context_size = 4
x = enc_sample[:context_size]        # [ 290, 4920, 2241,  287]
y = enc_sample[1:context_size + 1]   # [4920, 2241,  287,  257]
```

Which unrolls into a next-word prediction task at every position:

```
 and                        ---->  established
 and established            ---->  himself
 and established himself    ---->  in
 and established himself in ---->  a
```

Wrapped in a PyTorch `Dataset`, chunking the corpus with a sliding window:

```python
import torch
from torch.utils.data import Dataset, DataLoader

class GPTDatasetV1(Dataset):
    def __init__(self, txt, tokenizer, max_length, stride):
        self.input_ids, self.target_ids = [], []
        token_ids = tokenizer.encode(txt)

        for i in range(0, len(token_ids) - max_length, stride):
            input_chunk  = token_ids[i     : i + max_length]
            target_chunk = token_ids[i + 1 : i + max_length + 1]   # shifted by 1
            self.input_ids.append(torch.tensor(input_chunk))
            self.target_ids.append(torch.tensor(target_chunk))

    def __len__(self):
        return len(self.input_ids)

    def __getitem__(self, idx):
        return self.input_ids[idx], self.target_ids[idx]


def create_dataloader_v1(txt, batch_size=4, max_length=256, stride=128,
                         shuffle=True, drop_last=True, num_workers=0):
    tokenizer = tiktoken.get_encoding("gpt2")
    dataset = GPTDatasetV1(txt, tokenizer, max_length, stride)
    return DataLoader(dataset, batch_size=batch_size, shuffle=shuffle,
                      drop_last=drop_last,       # avoids loss spikes from a short final batch
                      num_workers=num_workers)
```

**The two knobs:**
- `max_length` — the context size (tokens per training example). 4 here for illustration; real training uses ≥ 256.
- `stride` — how far the window slides between examples.
  - `stride=1` → maximum overlap, each batch shifted one token from the last.
  - `stride == max_length` → **no overlap**, uses every token exactly once. This is the sensible default; more overlap risks overfitting.

```python
dataloader = create_dataloader_v1(raw_text, batch_size=8, max_length=4,
                                  stride=4, shuffle=False)
inputs, targets = next(iter(dataloader))
# inputs  shape: torch.Size([8, 4])
# inputs[0]  = [  40,  367, 2885, 1464]
# targets[0] = [ 367, 2885, 1464, 1807]   <- same row, shifted one left
```

Batch size is the usual tradeoff: small = less memory but noisier gradient updates.

### 2.7 Token embeddings
The embedding layer is **just a lookup table** — token ID *i* returns row *i* of a weight matrix. Weights start random and are optimized by backprop like any other layer.

```python
vocab_size, output_dim = 6, 3
torch.manual_seed(123)
embedding_layer = torch.nn.Embedding(vocab_size, output_dim)
# weight matrix: 6 rows (one per vocab token) x 3 columns (one per dim)

embedding_layer(torch.tensor([3]))
# tensor([[-0.4015, 0.9666, -1.1481]])   == row index 3 of the weight matrix

embedding_layer(torch.tensor([2, 3, 5, 1]))   # -> 4 x 3 matrix
```

> Equivalent to one-hot encoding followed by a matmul in a fully connected layer — just implemented far more efficiently. That equivalence is why it's differentiable and trainable.

Realistic sizing:

```python
vocab_size, output_dim = 50257, 256          # 256 dims; GPT-3 uses 12,288
token_embedding_layer = torch.nn.Embedding(vocab_size, output_dim)

token_embeddings = token_embedding_layer(inputs)   # inputs is [8, 4]
# torch.Size([8, 4, 256])   -> batch x tokens x embedding_dim
```

### 2.8 Encoding word positions
**The problem:** the embedding layer maps a token ID to the *same* vector regardless of position, and self-attention is itself position-agnostic. Without help, the model can't tell word order.

**The fix:** add a positional embedding to each token embedding.

| | Absolute | Relative |
|---|---|---|
| Encodes | The exact position (1st, 2nd, …) | The *distance* between tokens |
| Advantage | Simple, direct | Generalizes better to unseen sequence lengths |
| Used by | **GPT** (learned, not fixed) | — |

The original transformer used *fixed/predefined* positional encodings; **OpenAI's GPT models learn them during training.**

```python
context_length = max_length
pos_embedding_layer = torch.nn.Embedding(context_length, output_dim)
pos_embeddings = pos_embedding_layer(torch.arange(context_length))
# torch.Size([4, 256])   -> one vector per position, same dim as token embeddings

input_embeddings = token_embeddings + pos_embeddings   # broadcast across the 8 batches
# torch.Size([8, 4, 256])
```

`torch.arange(context_length)` is just a placeholder `[0, 1, ..., n-1]` — the position indices. `context_length` is the model's supported input size; longer text must be truncated.

`input_embeddings` is what feeds into the main LLM layers, starting in Ch. 3.

# Deep Dive A — How BPE Actually Works

The book says BPE "iteratively merges frequent pairs" and moves on. Here's the mechanism, verified against `tiktoken 0.14.0` / the `gpt2` encoding.

## The vocabulary is a *merge table*, not a word list

This is the thing that unlocks everything else. `SimpleTokenizerV1`'s vocab was `{word: id}` — a flat lookup. BPE's vocab is `{byte_sequence: rank}`, where **rank doubles as the token ID *and* as the order in which that merge was learned during training**. Low rank = learned early = frequent.

```python
ranks = enc._mergeable_ranks

# ranks 0-255: every raw byte. No merging involved — these are the atoms.
# ('!', 0) ('"', 1) ('#', 2) ... ('0', 15) ('1', 16) ...

# rank 256 onward: the actual learned merges, in frequency order
# (' t', 256) (' a', 257) ('he', 258) ('in', 259) ('re', 260) ('on', 261)
# (' the', 262) ('er', 263) (' s', 264) ('at', 265) (' w', 266) ...
```

Read that second row: the single most frequent adjacent byte pair in English web text is `" t"`, then `" a"`, then `"he"`. And `" the"` at rank 262 was built by merging `" t"` (256) + `"he"` (258) — **merges compose recursively into larger merges**.

**The vocab-size arithmetic:** `256 raw bytes + 50,000 learned merges + 1 special token (<|endoftext|>) = 50,257`.

## Two different algorithms: training vs. encoding

**Training (done once by OpenAI, never by us):**
1. Start with a vocabulary of the 256 possible bytes.
2. Count every adjacent pair across the whole corpus.
3. Merge the single most frequent pair into a new token; assign it the next rank.
4. Repeat 50,000 times.

**Encoding (what `enc.encode()` does at runtime)** — greedy, and it does *not* consult frequencies at all:
1. Split the byte sequence into individual bytes.
2. Look at every adjacent pair; find the one whose combination has the **lowest rank** in the table.
3. Merge it. Repeat until no adjacent pair exists in the table.
4. Emit the rank of each surviving chunk as the token ID.

Merging lowest-rank-first replays the merges in the same order training created them, which is what guarantees the encoding is deterministic and matches what the model was trained on.

## Watching it run

```python
def bpe_trace(word):
    parts = [bytes([b]) for b in word.encode("utf-8")]
    while len(parts) > 1:
        best, best_rank = None, None
        for i in range(len(parts) - 1):
            r = ranks.get(parts[i] + parts[i+1])       # is this pair in the table?
            if r is not None and (best_rank is None or r < best_rank):
                best, best_rank = i, r
        if best is None:
            break                                       # nothing left to merge
        parts[best:best+2] = [parts[best] + parts[best+1]]
    return [ranks[p] for p in parts]
```

`" unbelievable"` — 12 merges, collapsing all the way down to a **single** token:

```
start:          [' ', 'u', 'n', 'b', 'e', 'l', 'i', 'e', 'v', 'a', 'b', 'l', 'e']
merge  'le'   (rank   293) -> [' ','u','n','b','e','l','i','e','v','a','b','le']
merge  ' u'   (rank   334) -> [' u','n','b','e','l','i','e','v','a','b','le']
merge  'ab'   (rank   397) -> [' u','n','b','e','l','i','e','v','ab','le']
merge  'el'   (rank   417) -> [' u','n','b','el','i','e','v','ab','le']
merge  'ie'   (rank   494) -> [' u','n','b','el','ie','v','ab','le']
merge  'able' (rank   540) -> [' u','n','b','el','ie','v','able']      <- 'ab'+'le'
merge  ' un'  (rank   555) -> [' un','b','el','ie','v','able']
merge  'bel'  (rank  6667) -> [' un','bel','ie','v','able']
merge  'iev'  (rank 11203) -> [' un','bel','iev','able']
merge  ' unbel'     (17491) -> [' unbel','iev','able']
merge  ' unbeliev'  (20554) -> [' unbeliev','able']
merge  ' unbelievable' (24479) -> [' unbelievable']
final ids: [24479]
```

Note the ranks climb monotonically — small frequent fragments merge first, and those results feed larger, rarer merges.

`" Akwirw"` (the Exercise 2.1 gibberish) — merging stalls after 3 steps because no adjacent pair is in the table:

```
start: [' ', 'A', 'k', 'w', 'i', 'r', 'w']
merge ' A'  (rank  317) -> [' A','k','w','i','r','w']
merge 'ir'  (rank  343) -> [' A','k','w','ir','w']
merge ' Ak' (rank 9084) -> [' Ak','w','ir','w']
final ids: [9084, 86, 343, 86]     # [' Ak', 'w', 'ir', 'w']
```

The leftover `'w'` tokens are just **raw bytes** — rank 86 is the byte `w`. That's the fallback, and it's why the process can never fail.

## Why BPE never needs `<|unk|>`

**Because the vocabulary bottoms out at all 256 possible byte values.** Any conceivable input — any language, emoji, binary garbage — is a sequence of bytes, and every byte has a token. Merging is pure optimization on top of a base case that always exists. Worst case you get one token per byte; you never get a failure.

Contrast with `SimpleTokenizerV2`, where `"Hello"` → `<|unk|>` destroys information irreversibly. BPE is **lossless**: `decode(encode(x)) == x` always.

```python
enc.encode(" someunknownPlace")   # [617, 34680, 27271] -> [' some', 'unknown', 'Place']
```

Even a coined word gets decomposed into *meaningful* pieces the model has representations for — so it can infer something about it. Common words stay one token (efficient); rare words fragment (still representable). That's the tradeoff BPE is buying.

## Two details the book skips

**1. Leading spaces are part of the token.**

```python
enc.encode("cat")     # [9246]  -> ['cat']
enc.encode(" cat")    # [3797]  -> [' cat']       DIFFERENT token
enc.encode("  cat")   # [220, 3797] -> [' ', ' cat']
```

`"cat"` and `" cat"` are distinct tokens with unrelated IDs. This is how BPE encodes whitespace losslessly without wasting a token on every single space — the space rides along on the following word. (Practical consequence: a trailing space in a prompt changes tokenization and can degrade output.)

**2. Pre-tokenization runs first.** Before any merging, tiktoken splits text with a regex on word/punctuation/whitespace boundaries. Merges only happen *within* those chunks, never across them — so `"the"` + `"cat"` can never merge into `"thecat"` no matter how often that pair appears. This bounds the merge search and keeps tokens linguistically sane.

**Why tiktoken is fast:** the merge loop above is O(n²) per chunk in Python. tiktoken implements it in Rust with pre-tokenization chunking the work into small independent pieces that parallelize.

# Deep Dive B — How Positional Embeddings Actually Work

> *"Are the token embeddings including a positional vector or something else to each token vector to indicate its position — in what sense?"*

Short answer: **a separate learned vector per position slot, element-wise added to the token vector.** Not concatenated, not a flag, not a modification of the token embedding itself. Let me unpack why that's not as crazy as it sounds.

## Two independent lookup tables

```python
tok_emb = torch.nn.Embedding(vocab_size,     output_dim)   # 50257 rows — indexed by TOKEN ID
pos_emb = torch.nn.Embedding(context_length, output_dim)   #     4 rows — indexed by SLOT INDEX
```

They're the same kind of object (a lookup table), but **keyed on completely different things**:

| | `tok_emb` | `pos_emb` |
|---|---|---|
| Row count | vocab size (50,257) | context length (e.g. 1024) |
| Indexed by | *which word* it is | *where* it sits (0, 1, 2, …) |
| Input | `inputs` — the token IDs | `torch.arange(context_length)` — always `[0,1,2,...]` |
| Depends on the text? | Yes | **No** — same every forward pass |

That `torch.arange` is the tell. It's a constant. `pos_emb` row 3 means "the 4th slot in the sequence" and returns the identical vector whether that slot holds `"cat"`, `"the"`, or `<|endoftext|>`.

## The addition, concretely

Tiny example — `vocab_size=10`, `output_dim=4`, token ID **7 appears at both position 0 and position 3**:

```
token ids: [7, 2, 4, 7, 1]

token embeddings — rows 0 and 3 are IDENTICAL (same token id 7):
  [-0.8199, -0.4210, -0.9620,  1.2825]   <- pos 0, token 7
  [ 0.7671, -1.1925,  0.6984, -1.4097]
  [-0.0770, -1.0205, -0.1690,  0.9178]
  [-0.8199, -0.4210, -0.9620,  1.2825]   <- pos 3, token 7  (same!)
  [ 0.3486,  0.6603, -0.2196, -0.3792]

positional embeddings — one row per SLOT, nothing to do with the tokens:
  [-0.2044, -2.2685, -0.9133, -0.4204]   <- "I am position 0"
  [ 0.2436, -0.0567,  0.3784,  1.6863]   <- "I am position 1"
  [ 0.2553, -0.5496,  1.0042,  0.8272]
  [ 1.5434,  0.1406,  1.0617, -0.9929]   <- "I am position 3"
  [-1.6025, -1.0764,  0.9031, -0.7218]

sum — rows 0 and 3 are now DIFFERENT:
  [-1.0244, -2.6896, -1.8753,  0.8621]   <- pos 0, token 7
  [ 1.0107, -1.2492,  1.0768,  0.2766]
  [ 0.1783, -1.5701,  0.8353,  1.7450]
  [ 0.7235, -0.2805,  0.0997,  0.2896]   <- pos 3, token 7  (no longer identical)
  [-1.2539, -0.4160,  0.6835, -1.1010]
```

```python
torch.equal(t[0], t[3])   # True  — before adding position
torch.equal(x[0], x[3])   # False — after
```

**That's the entire mechanism.** The same word in two places now has two different vectors, and the difference between them is exactly `pos_emb[3] - pos_emb[0]`.

Shapes: `[8, 4, 256] + [4, 256] → [8, 4, 256]`. The positional tensor broadcasts across the batch — every sequence in the batch gets the same positional vectors, which is correct, since position 2 means the same thing in every sequence.

## Why this is *necessary*, not just nice

The real justification is stronger than "the model can't tell word order." Without positional info, **self-attention is permutation-equivariant**: attention computes a weighted sum over all tokens, and addition is commutative, so shuffling the input tokens produces the identically-shuffled output. Nothing in the mechanism can distinguish `"dog bites man"` from `"man bites dog"` — a transformer without positional embeddings is a **bag of words**.

This is a real architectural hole, not a refinement. RNNs never had it (they consume tokens in order by construction); transformers gave up sequential processing to get parallelism, and positional embeddings are the price.

## Why *addition* and not concatenation?

Concatenation would seem more natural — keep the two signals in separate dimensions, no interference. Two reasons addition wins:

1. **It's free.** Concatenating a 256-dim position to a 256-dim token gives 512 dims, doubling the width of every downstream matrix and roughly quadrupling attention cost. Addition keeps `d_model` fixed.
2. **In high dimensions there's room.** In 256+ dims, the model can learn to keep token content and positional signal in near-orthogonal subspaces — effectively getting concatenation's separation without paying for the width. The `Q`/`K` projections in attention can then learn to read position out of the sum. Nothing *enforces* this; it's learned because it's useful.

It looks lossy and isn't, in practice. Empirically it just works, which is the actual reason everyone does it.

## Learned vs. fixed — and the catch

The original transformer used **fixed sinusoidal** encodings (sines/cosines of varying frequency), computed by formula, not learned. GPT instead makes `pos_emb` a plain `nn.Embedding` whose weights are trained by backprop like everything else.

The vectors are **arbitrary** — position 3's vector isn't "3" in any readable sense, and positions 3 and 4 aren't necessarily close together in the space. It's a set of learned, mutually distinguishable tags. The model just needs them to be *consistent*, which they are, since they're the same every forward pass.

**The catch, and it's a big one:** `nn.Embedding(context_length, output_dim)` allocates a **fixed number of rows**. There is no row for position 1025 in a 1024-context model, so the model physically cannot process a longer sequence — you must truncate. Learned absolute positions cannot extrapolate at all.

This limitation is precisely what **relative** positional schemes fix, by encoding *distance between* tokens rather than *absolute slot*. Modern models (Llama, and most things post-2022) use **RoPE** (rotary embeddings), which rotates `Q`/`K` by an angle proportional to position — making attention scores depend only on relative offset, and allowing context extension well past the training length. The book sticks to GPT-2-style learned absolute embeddings; just know this is the one component of the architecture that's genuinely dated.
