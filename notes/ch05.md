## 5.1 Evaluating generative text models

**Loss** - used to monitor the model's performance during the training phase. It serves as a progress and success indicator of the training progress.

→ it is one number per batch, so it can be printed every few steps and plotted
→ a loss near 0 means the model puts almost all its probability on the token that actually came next

### The config changes

One value moves from chapter 4:

```python
"context_length": 256,   # was 1024
```

The 1024-token context is what GPT-2 was trained with, and it makes the run too slow and too memory-hungry for a laptop. 256 is purely a practical cut. 5.5 switches it back to 1024 when the pretrained OpenAI weights get loaded, because those weights include a $1024 \times 768$ positional table that will not fit a 256-row slot.

The book also notes `drop_rate` can be set to 0, which is common. Leaving it at 0.1 is fine for now.

## 5.1.1 Using GPT to generate text

Two helpers, so the rest of the chapter can move between text and token IDs without repeating itself.

```python
def text_to_token_ids(text, tokenizer):
    encoded = tokenizer.encode(text, allowed_special={'<|endoftext|>'})
    encoded_tensor = torch.tensor(encoded).unsqueeze(0)
    return encoded_tensor

def token_ids_to_text(token_ids, tokenizer):
    flat = token_ids.squeeze(0)
    return tokenizer.decode(flat.tolist())
```

`unsqueeze(0)` adds the batch dimension, `(n,)` becomes `(1, n)`. `squeeze(0)` takes it back off. These are the same two lines that were inlined in `generate.py` in 4.7, pulled out so they stop being copy-pasted.

**`allowed_special`** matters. `tiktoken` raises `ValueError` on `<|endoftext|>` by default, because silently encoding a control token that appeared in user text is a security-shaped bug. Passing the set says this one is deliberate. Chapter 5 needs it because `<|endoftext|>` is the separator between documents.

Measured, with `context_length: 256` and `manual_seed(123)`:

```
Every effort moves you rentingetic wasnم refres RexMeCHicular stren
```

Matches the book. Still gibberish, still correct, the weights are still random.

## 5.1.2 Calculating the text generation loss

### Generating text

In generating text, the next predicted word can be obtained by applying the **softmax function** to the logits output from the model, and transform them into probability scores. Initially, the model outputs gibberish because the probabilities of the output token is roughly around 1/ `no. of tokens`.

→ "no. of tokens" here is the vocabulary size, not the length of the prompt
→ $1/50257 \approx 0.00002$, so every token in the vocabulary starts out about equally likely

The goal of training an LLM is to maximize the likelihood of the correct token. We can maximize the softmax probability values corresponding to the target token by updating the model weights so that the model outputs higher values for the respective token IDs we want to generate, in a process called **backpropagation**.

**Backpropagation** - algorithm used during the training phase, by calculating the error gradient for each parameter and updating the weights. Requires a loss function. In this case, the loss function is the **difference** between the **model's predicted output** and the **actual desired output** (basically the distance between the 2 objects).

→ strictly, backprop computes the gradients and the optimizer applies them. 5.2 introduces AdamW, which is the part that actually writes new values into the weights
→ the mechanics of the backward pass are in the background section of [ch04](ch04.md), each layer multiplies its local derivative into the gradient handed down from above

### The worked example

Two sequences of three tokens each, already as IDs:

```python
inputs  = torch.tensor([[16833, 3626, 6100],   # "every effort moves"
                        [   40, 1107,  588]])  # "I really like"

targets = torch.tensor([[3626, 6100,   345],   # " effort moves you"
                        [1107,  588, 11311]])  # " really like chocolate"
```

The targets are the inputs shifted one position left, exactly what `GPTDatasetV1` produces. Nothing new, it is just written out by hand here so the loss can be followed by eye.

### Six steps from logits to one number

Measured throughout, all values reproduce the book.

| step | operation | result |
| --- | --- | --- |
| 1 | `model(inputs)` | logits, `(2, 3, 50257)` |
| 2 | `softmax(logits, dim=-1)` | probas, `(2, 3, 50257)` |
| 3 | index out the target probabilities | 6 numbers |
| 4 | `torch.log` | 6 log probabilities |
| 5 | `torch.mean` | $-10.7940$ |
| 6 | multiply by $-1$ | $10.7940$ |

Step 3 is the one worth reading twice:

```python
target_probas_1 = probas[text_idx, [0, 1, 2], targets[text_idx]]
```

Three indices at once. The first picks the sequence, the second picks each of the three positions, the third picks the column named by the target ID at that position. It pulls out "what probability did the model give to the token that was actually correct", once per position.

Measured:

| | position 0 | position 1 | position 2 |
| --- | --- | --- | --- |
| text 1 | 7.454e-05 | 3.106e-05 | 1.156e-05 |
| text 2 | 1.034e-05 | 5.678e-05 | 4.756e-06 |

All six sit near the $0.00002$ baseline, which is the numeric version of "the model has no idea".

### Why the logarithm

We apply logarithm to the probability score because this makes it more manageable in mathematical optimization than handling the scores directly ie. turn multiplication into addition, preventing underflow (between 0 and 1). We want the average of log probability of the output be as close to 0 as possible.

→ underflow is the real one here. The probability of a whole sequence is the product of its per-token probabilities, and a few hundred numbers around $10^{-5}$ multiplied together is $0$ in float32
→ $\log(1) = 0$ and $\log(x) \to -\infty$ as $x \to 0$, so a log probability of $0$ means perfect confidence in the right token and there is no way to do better
→ measured, the six log probabilities are $-9.5042$, $-10.3796$, $-11.3677$, $-11.4798$, $-9.7764$, $-12.2561$

The average is $-10.7940$. Convention in deep learning is to minimise rather than maximise, so the sign gets flipped and $10.7940$ is the number that gets reported.

**Cross entropy loss** - measures the difference between 2 probability distributions, the true distribution of the labels and the distribution from the predicted values from models. The same as the **negative average log probability**.

### Doing it in one call

PyTorch collapses all six steps:

```python
loss = torch.nn.functional.cross_entropy(logits.flatten(0, 1), targets.flatten())
```

Measured, $10.793964$ against the hand-computed $10.793963$, equal to float precision.

**`flatten(0, 1)` merges the batch and token axes.** `cross_entropy` wants predictions as `(N, C)` and labels as `(N,)`, so `(2, 3, 50257)` becomes `(6, 50257)` and `(2, 3)` becomes `(6,)`. Six independent next-token predictions, and it no longer matters which sequence each came from.

**It takes logits, not probabilities.** `cross_entropy` runs `log_softmax` internally. Handing it `probas` would apply softmax twice and quietly give the wrong number, with no error. The softmax written out in step 2 exists to show the idea, not to be fed forward.

### Perplexity

**Perplexity** - evaluate the performance of models. Usually used alongside cross entropy loss. It measures how well the probability distribution predicted by the model matches the actual distribution. **Low perplexity -> model predictions are closer to the actual distribution**.

$\text{perplexity} = e^{\text{loss}}$

→ measured, $e^{10.7940} = 48{,}725.82$
→ it reads as an effective vocabulary size. The model is behaving as if it were guessing uniformly among 48,725 tokens at each step
→ that is the useful part. A loss of 10.79 means nothing on its own, but "picking blind from 48,725 options" is a sentence you can picture
→ the floor is 1, meaning total certainty. Against a 50,257-token vocabulary, 48,725 is almost exactly the no-knowledge case

## 5.1.3 Calculating the training and validation set losses

### The dataset

"The Verdict" by Edith Wharton, the same file from chapter 2. Measured, 20,479 characters and 5,145 tokens.

That is tiny, deliberately. It runs in minutes on a laptop instead of weeks on a cluster. For scale, the book puts Llama 2 7B at 184,320 A100 hours over 2 trillion tokens, roughly \$690,000 of rented compute.

### Splitting

```python
train_ratio = 0.90
split_idx = int(train_ratio * len(text_data))
train_data = text_data[:split_idx]
val_data = text_data[split_idx:]
```

The split is on characters, not tokens, and it is a straight cut rather than a shuffle. Measured, 4,612 training tokens and 534 validation tokens. The validation set is the last tenth of the story, so it is genuinely unseen text rather than a random sample of the same paragraphs.

### The two loaders

```python
train_loader = create_dataloader_v1(
    train_data, batch_size=2,
    max_length=GPT_CONFIG_124M["context_length"],
    stride=GPT_CONFIG_124M["context_length"],
    drop_last=True, shuffle=True, num_workers=0)

val_loader = create_dataloader_v1(
    val_data, batch_size=2,
    max_length=GPT_CONFIG_124M["context_length"],
    stride=GPT_CONFIG_124M["context_length"],
    drop_last=False, shuffle=False, num_workers=0)
```

`stride == max_length` means no overlap, every token is used exactly once. Leaving `stride` at its default of 128 would slide the window in half-steps and train on each token twice.

The two loaders differ on purpose:

| | train | val | why |
| --- | --- | --- | --- |
| `shuffle` | `True` | `False` | batch order should not be a pattern the model can learn. Validation is only measured, so order is irrelevant |
| `drop_last` | `True` | `False` | a short final batch gives a noisier gradient. Nothing is learned from validation, so throwing data away there would only make the estimate worse |

Measured at `context_length = 256`: 9 training batches and 1 validation batch, every one of shape `(2, 256)`.

### Computing the loss over a loader

```python
def calc_loss_batch(input_batch, target_batch, model, device):
    input_batch = input_batch.to(device)
    target_batch = target_batch.to(device)
    logits = model(input_batch)
    return torch.nn.functional.cross_entropy(
        logits.flatten(0, 1), target_batch.flatten())


def calc_loss_loader(data_loader, model, device, num_batches=None):
    total_loss = 0.
    if len(data_loader) == 0:
        return float("nan")
    elif num_batches is None:
        num_batches = len(data_loader)
    else:
        num_batches = min(num_batches, len(data_loader))
    for i, (input_batch, target_batch) in enumerate(data_loader):
        if i < num_batches:
            loss = calc_loss_batch(input_batch, target_batch, model, device)
            total_loss += loss.item()
        else:
            break
    return total_loss / num_batches
```

**`.to(device)` on the batches.** The model was moved to the device once. The batches come off the loader on the CPU every iteration, so they have to be moved every iteration too.

**`.item()` pulls a Python float out of the tensor.** Without it, `total_loss` would hold on to the autograd graph of every batch at once, and the memory would grow with the loop.

**`num_batches` caps the work.** Evaluating all 9 batches between every training step would dominate the runtime, so 5.2 calls this with a small number to get a cheap estimate.

**The `nan` guard** is the empty-loader case. Returning `nan` instead of raising `ZeroDivisionError` is deliberate, an empty validation set is a config problem rather than a crash.

### The numbers

Measured, with `model.eval()` and `torch.no_grad()`:

```
Training loss:   10.98758348
Validation loss: 10.98110676
```

Both match the book. Both sit near $\ln(50257) = 10.825$, which is the loss of a model that outputs a flat distribution. Slightly above it, because random weights are not quite flat and being confidently wrong costs more than being uncertain.

Train and validation being nearly equal is expected and means nothing yet. An untrained model is equally bad at both. The gap opening up is what 5.2 watches for, because that gap is overfitting.

### Three ways to get this wrong

Measured, all three:

- **Forgetting `model.eval()`.** Dropout stays on, so the loss is random. Two runs on the same data gave 10.9907 and 10.9836. In eval mode both runs gave 10.9876. The loss is supposed to be a measurement, and a measurement that moves when nothing changed is useless.
- **Leaving `context_length` at 1024.** The training set holds 4,612 tokens, so a 1024-token window yields 4 examples and 2 batches. The validation set holds 534 tokens, fewer than one window, so it yields **zero** batches and `calc_loss_loader` returns `nan`. The config drops to 256 for this reason as much as for speed.
- **`torch.device("mps" if torch.cuda.is_available() else "cpu")`.** On Apple silicon `torch.cuda.is_available()` is `False`, so this always falls through to CPU and the MPS branch is unreachable. The check for Metal is `torch.backends.mps.is_available()`, measured `True` on this machine.

## Where this lands

There is now a single number that says how good the model is, computed the same way on data it trains on and data it does not. Nothing has been trained.

The number to beat is 10.99, and the floor is 0. 5.2 adds the loop that pushes it down: AdamW, an epoch over the training batches, and a print of both losses every few steps so the two curves can be watched separating.
