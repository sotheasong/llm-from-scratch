## 5.1 Evaluating generative text models

**Loss** - a numerical value that measures how wrong a model's prediction is compared to the actual target value. A success indicator.

**Training losses** - a metric that measures how well a machine learning or deep learning model fits the **training data**.

**Validation losses** -  on validation data, unseen testing data.

### 5.1.1 Using GPT to generate text

3 step process to generate text

1. Tokenizer converts input text into a series of token IDs

2. Model receives the token IDs and generates corresponding logits (vectors representing the probability distribution of each token in the vocabulary).

3. Logits are converted back into token IDs (tokenizer decodes back into text).

Use vocabulary (text bank) to map the **input text to token IDs**. Obtain the seven-dimensional probability row vector (**logit**) for each input to via the **softmax function**. Use **argmax** to find the index position with the highest probability in each row vector. Convert the token IDs at these index position into **predicted text**.

Currently without any evaluation and no way to assess the performance of the model, it generates incoherent text. We can monitor and enhance the model's performance through *loss*.

### 5.1.2 Calculating the text generation loss

We can evaluate the performance/quality of the model by calculating the **text generation loss**. 

We can use this loss to construct a **training function**, used to update the model's weight to improve the generated text. Part of the **text evaluation** implemented is to measure "how far" the generated tokens are from the correct targets. The training function will use these values to adjust the model weights to generate text that is more similar to the correct targers.

Since our compact seven-token vocabulary is smaller compared to the vocabulary used to actually train GPT-2, the random evaluated values will hover around 1/7 compared to 1/50,257.

The goal of training an LLM is to **maximize the likelilhood of the correct token**, ie. increasing the probability of the correct token relative to other tokens. The process of updating the model weights is called **backpropagation**. Which requires a loss function, which calculates the difference between the model's output and the desired output. 

**Cross entropy loss** - negative average log probability loss. Measures the difference between 2 probability distributions eg. true distribution of labels and predicted distribution from models. 

**Perplexity** - used alongside cross entropy to evaluate the performance of models. Provide interpretability on how the uncertainty of a model in predicting the next token eg. tensor(48725.8203) - translate to the model being unsure about which among 48,725 tokens in the vocabulary to generate as the next token.

### 5.1.3 Calculating the training and validation set losses

Divide the dataset into a **training** and **validation set** and use data loaders to prepare the batches for LLM training. **Data loaders** - batches the dataset, feeds text, token sequences, and target labels into a model in structured, manageable pieces (mini-batches) during training, fine-tuning, or evaluation.

## 5.3 Decoding strategies to control randomness

Finding strategies to generate more original text. 

### 5.3.1 Temperature scaling

**Temperature scaling** - adds probabilistic selection process to the next-token generation task. Before we used **greedy decoding** - sampling the token with the highest probability as the next token. We can add varity by replacing argmax with a function that samples from a probability distribution.

Inside `generate_text_simple`, we convert the logits into probabilities via the softmax function and obtain the token ID corresponding to the generated token via the argmax function which we can convert back into text. 

**Probabilistic sampling process** - elects a subset of a population using random mechanisms so that every unit has a known, non-zero chance of selection

For a **probabilistic sampling process**, we replace argmax with **multinomial function**. The multinomial function samples the next token proportional to its probability score. 

We can control the distribution and selection process using **temperature scaling**. Temperatures greater than 1 result in more uniformly distributed token probabilities, and temperatures smaller than 1 will result in more confident distributions. 

![](/Users/sothea/Library/Application%20Support/marktext/images/2026-11-22-15-37-15-image.png)

Decreasing the temperature to 0.1 sharpens the distribution, so the most likely token will have an even higher probability score. Increasing the temperature to 5 makes the distribution more uniform.

A temperature of 1 divides the logits by 1 before passing them to *softmax* ie. it is the same as not using temperature scaling. 

**Higher temperature** -> **uniformly distributed** - more diverse outputs as it reduces the likelihood of the model repeatedly selecting the most probable token. This also leads to incorrect sentences.

### 5.3.2 Top-k sampling

**Top-k sampling** - a text-generation decoding method that restricts a language model's next-token choices to only the **k** highest-probability tokens. Combined with probabilistic sampling and temperature scaling improves the text generation. 

We restrict which tokens can be sampled by masking their probability score. 

![](/Users/sothea/Library/Application%20Support/marktext/images/2026-11-23-16-28-38-image.png)

Top-k replaces all logits with negative infinity value so that when computing the softmax values, the probability score is 0 and the rest sum up to 1.

## 5.4 Loading and saving model weights in PyTorch

Pretraining LLMs is computationally expensive, so we save the LLM so that we don't have to retrain the model every time.

![](/Users/sothea/Library/Application%20Support/marktext/images/2026-11-24-17-50-50-image.png)

**state_dict** - a dictionary mapping each layer to its parameters. Saving this is the recommended way since it holds the numbers and nothing else. The architecture is not in the file, so loading means building a fresh model from the same config first, then loading the weights into it. A config that does not match the saved one fails at this point. `.pth` is the filename convention for PyTorch.

**map_location** - decides which device the tensors land on when loading. Without it they try to return to the device they were saved from.

Saving the weights on their own is enough to use the model again later. We switch to evaluation mode after loading, which disables dropout. Dropout randomly drops neurons during training to prevent overfitting, but at inference we do not want to discard anything the network learned.

Continuing training later needs the **optimizer state** saved alongside the weights. AdamW keeps a running mean and variance per parameter and uses that history to adapt the learning rate for each weight separately. Dropping it resets those estimates, so the optimizer starts guessing again and the model may learn suboptimally or fail to converge. Both go into one dictionary, one key for the model state and one for the optimizer state.

Restoring both has an order to it. Build the model, load its weights, build the optimizer against that model's parameters, then load the optimizer state. The optimizer state is keyed by parameter position, so the optimizer has to be attached to the right parameters before the state goes in. We switch back to training mode at the end, which puts dropout back on. The step count carries across, 90 after ten epochs, which is the sign the history survived.

## 5.5 Loading pretrained weights from OpenAI

**settings** - the contents of `hparams.json`, the architecture GPT-2 was actually trained with. For the 124M model that is `n_vocab` 50257, `n_ctx` 1024, `n_embd` 768, `n_head` 12 and `n_layer` 12. Our config has to match these before the weights will fit.

**params** - the numbers themselves, as a nested dictionary of numpy arrays. Four entries sit at the top level alongside a list of twelve blocks, one per transformer layer, 148 arrays in total.

```
wte              (50257, 768)   token embedding
wpe              (1024, 768)    positional embedding
g, b             (768,)         final layer norm
blocks           12 dicts, one per transformer layer
  ln_1/g, ln_1/b   (768,)        norm before attention
  attn/c_attn/w    (768, 2304)   query, key and value stacked together
  attn/c_attn/b    (2304,)
  attn/c_proj/w    (768, 768)    attention output projection
  attn/c_proj/b    (768,)
  ln_2/g, ln_2/b   (768,)        norm before feed forward
  mlp/c_fc/w       (768, 3072)   feed forward expansion
  mlp/c_fc/b       (3072,)
  mlp/c_proj/w     (3072, 768)   feed forward contraction
  mlp/c_proj/b     (768,)
```

OpenAI's names are terse. `wte` is the token embedding and `wpe` the positional embedding. `g` and `b` are gain and bias, their words for the scale and shift of a layer norm. The blocks are named `h0` through `h11` in the checkpoint, which the loader has already collected into the `blocks` list. `c_attn` and `c_proj` are the attention input and output projections, and `c_fc` is the feed forward expansion.

Two things make the mapping awkward. `c_attn` packs the query, key and value matrices into one `(768, 2304)` array, so it has to be split three ways before it can go into our three separate linear layers. And every weight matrix is stored transposed relative to what `nn.Linear` expects, so each one needs a transpose on the way in.

Our config needs two changes before the weights fit. `context_length` goes back to 1024, since we shortened it to 256 in 5.1.1 and GPT-2 was trained at the full length. `qkv_bias` becomes True, because OpenAI used bias vectors in the query, key and value projections and we had them turned off.

Four sizes are available, 124M, 355M, 774M and 1558M. They differ only in `emb_dim`, `n_layers` and `n_heads`, so one loading function covers all of them.

![](/Users/sothea/Library/Application%20Support/marktext/images/2026-11-25-19-48-00-image.png)

**assign** - checks that the shape being written into matches the shape of the array coming in, then wraps that array as a `Parameter`. This shape check is the only guard rail in the whole process.

**load_weights_into_gpt** - walks the params dictionary and copies every array into the matching place in our model. The two embeddings first, then each of the twelve blocks in turn, then the final layer norm and the output head.

Within a block the order follows the structure above. Split `c_attn` three ways into query, key and value and copy their weights and biases, copy the attention output projection, copy the two feed forward layers, then the two layer norms. The GELU between the feed forward layers holds no numbers, so nothing goes into it.

**Weight tying** - the output head reuses the token embedding instead of having a matrix of its own. The same 50257 by 768 array serves both ends, turning token IDs into vectors on the way in and vectors back into token scores on the way out. Without it the model has 163,037,184 parameters, and sharing that one matrix brings it down to 124,439,808, which is where the name 124M comes from.

Nothing is learned in this section. Every number is read off OpenAI's checkpoint and placed into our own architecture, so this is a copy rather than training.

A forgotten assignment raises nothing. `assign` only compares shapes, and any layer left out keeps the random values it was initialized with, which already have the right shape. The model still runs and still produces text, the text is just nonsense. Leaving out the four feed forward lines gave repeated junk like "millions trillions trillion billions" instead of a sentence, with no error anywhere. The check is whether the output reads as English, not whether anything crashed.

With the weights in place, generating with top-k 50 and temperature 1.5 gives coherent text from a model we never trained.
